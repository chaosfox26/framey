# Experimental Decky package compatibility

Framey has an independently implemented compatibility prototype for selected original Decky packages. It does not install Decky Loader, React, ReactDOM, Preact or Decky's UI library. A Framey-owned DOM renderer supplies a tested subset of element, state, effect and component behavior; a separate host translates plugin calls and selected controls into Framey's services.

This is an experimental compatibility profile. Builds that include the runtime offer an explicit, confirmed import from Decky Store details; older builds retain browse-and-inspect behavior. Importing a package does not establish that its functions are compatible. Device-provider discovery and its limits are documented separately in [Steam Frame integration](steam-frame-integration.md).

## Import from the Decky Store

Open **Decky Store**, choose a package and version, then select **Review experimental import**. The review explains the partial support before **Import experimental profile** starts an installation. Cancelling the review does not download or execute the package. The testing catalog still requires developer mode.

Framey binds confirmation to the exact source, listing and version. Import downloads the selected archive again, checks its digest and bounded archive rules, and derives the destination from the store listing. Only new installations are supported: an existing plugin, backup, staging directory or pending operation is not overwritten. Failed startup removes only the owned new installation; ambiguous cleanup retains files for recovery. Pending imports and matching results survive reopening the Store.

A successful import means the package was installed and its backend passed the installation startup check. It does not mean every control, Steam integration or hardware function works. Browsing and **Inspect compatibility** remain read-only; only confirmed import enters the trusted-plugin lifecycle. Original files and attribution remain in the installed package.

## Import an original package

Use an original ZIP and the SHA-256 for that exact store version. Inspection never executes the plugin. Run from a Framey checkout:

```sh
python3 tools/framey_decky.py inspect plugin.zip --sha256 <store-sha256>
python3 tools/framey_decky.py import plugin.zip --sha256 <store-sha256> --id decky-example --output /path/to/new-folder
```

The output directory must be new, with an existing parent, and cannot pass through a symbolic link. The importer refuses privilege flags, native binaries, declared remote-binary downloads and unknown backend API versions in this initial profile. These checks bound the profile; they do not review the plugin's Python or JavaScript for all possible behavior.

The generated folder has ordinary Framey `plugin.json`, `main.js` and optional `backend.py` entry points. Its `vendor/decky` directory retains the original package entries, including licenses and notices, without rewriting the original frontend or backend files. `decky-provenance.json` records the original archive digest, per-file hashes, source version and unverified capabilities. Store imports additionally record a source/version-bound catalog receipt. The frontend loader wraps original JavaScript in a separate plugin realm; modern ESM and legacy IIFE factories are supported. Supported modern multi-file ESM packages use the managed JavaScript graph described below; single-file ESM and legacy IIFE packages keep their existing loader paths. A bounded package-local PNG map resolves selected original image URLs inside the owned iframe; it does not supply a general Decky asset server.

After reviewing and testing the package, installing the generated directory follows the normal trusted Framey plugin-folder workflow. The importer itself does not install into the headset or reload running services. Preserve original authorship, licenses and notices; a compatibility wrapper does not make the original plugin Framey-authored.

## Managed multi-file JavaScript

Current development source adds a bounded native ESM path for modern packages containing multiple JavaScript files under `dist/`. The importer records the selected files and their hashes in provenance without rewriting original JavaScript. Framey's native issuer derives the installed package and files from the enabled caller and managed provenance, verifies their hashes, then serves an immutable byte snapshot from an owned loopback listener. The browser imports the original entry in the plugin's owned iframe, so supported relative static and dynamic `.js` imports retain normal URL and module-identity behavior. This does not provide arbitrary files, remote modules, CSS, fonts, JSON modules, bare-package resolution or general Decky asset routes. Inspection checks the bounded file profile; it does not parse or prove every import or execute the package.

The profile permits at most **64 JavaScript files, 2 MiB per file and 8 MiB per package**, with a **16 MiB aggregate resident/capture budget**. Only canonical supported `.js` paths below `dist/` qualify. Unsupported module paths or sizes block the multi-file import profile; privilege, native-binary and other archive gates still apply. Native issuance uses current caller identity and generation, fixed origin policy and exact-token revocation. Renewals recheck provenance and original bytes. Plugins cannot choose filesystem roots, listener addresses, source code or lease duration through this API.

A code lease lasts **600 seconds**, with a Framey SDK renewal attempt every **240 seconds** while the surface remains active. Long sleep, delayed execution, source changes or caller replacement can lose the lease. Loss fails the owned graph explicitly and requires reopening the plugin; expired leases are not revived automatically. Disposal releases the graph, iframe, pending waits and owned resources. Cleanup cannot interrupt JavaScript already executing inside the browser. Capability URLs and tokens are private resources and are excluded from exposed graph diagnostics. These are development-source contracts; the dated evidence below distinguishes local checks, original-package acceptance and device feasibility.

## Framey-owned version-specific repairs

Current development source adds a fixed Framey-owned repair registry for the known Storage Cleaner backend's `delete_cache` defect. It matches the exact original source digest and loaded class, method, code, globals and signature contracts; the chosen Framey installation ID grants no patch authority. Unknown source stays unchanged. Recognized source with a mismatched runtime or home contract fails explicitly. This is one version-specific repair, not a general backend-rewriting interface.

Generated backend wrappers load a separate Framey-owned helper beside the wrapper, verify its bound SHA-256 and load it before entering the original package context. The helper remains outside `vendor/decky`. Provenance records its ownership, registry and digest separately; startup metadata records applied patch IDs and path profile. Original archive identity, vendor hashes, source bytes, licenses, frontend paths and profile-1 eligibility remain unchanged.

The repair accepts exactly `shadercache` or `compatdata`, optionally followed by a canonical positive 32-bit decimal app ID. The whole-cache forms delete the selected cache directory; app-specific forms delete only that app directory. It supports the ordinary primary `~/.steam/steam` alias and requires real normal-user-owned home and cache directories. Cache/app aliases, mount crossings, unsupported ownership, special entries and traversal beyond depth 32 or 200,000 entries fail explicitly. Descendant symlink names are unlinked without following their targets; unlinking a cache hardlink name preserves the outside file's contents. Accepted deletion work serializes and its worker thread drains before the coroutine completes, including cancellation. This supplies no rollback, cross-process lock, malicious concurrent-rename guarantee or immediate-stop guarantee after a caller timeout or process death.

## Legacy fetch and TLS helper profile

Current development source adds an ordinary-JSON profile for legacy `serverAPI.fetchNoCors`. An omitted or falsy method defaults to `POST`. A supplied `json` value is serialized into the request body; the adapter adds `application/json` when the caller has not supplied a content type. Supplying both `json` and `body`, or an unserializable value, fails explicitly. A completed request returns `{ success: true, result: { body, status, headers } }`, with body text, HTTP status and the filtered header map supplied by Framey's existing transport. Completed HTTP 404 and 503 replies remain outer transport successes; callers must inspect `status`. Transport, body-reading or admission failures return `{ success: false, result: "Legacy fetch failed" }` without exposing private transport errors.

Modern `fetchNoCors` and the plugin realm's `fetch` keep their existing `Response` path and options. The legacy profile does not reproduce raw aiohttp bytes, charset decoding, unfiltered headers, custom serialization or every upstream option. Existing Framey network permissions, filters and bounds still apply; this adapter provides no network-policy bypass.

The Framey-provided Python `helpers.get_ssl_context()` creates a fresh verified TLS client context using platform trust defaults, with server-certificate and hostname verification. SSL support is optional at bridge startup: when unavailable, unrelated helpers and startup remain usable, while calling this helper raises an explicit unavailable error. It has no insecure fallback. The bridge captures its trusted SSL module before entering the original package context; owned tests cover bundled `ssl`/`_ssl` shadows and primed module-name replacements. That capture does not make the trusted module immune to direct mutation. Bundled original `helpers` modules retain precedence. This fresh platform-trust profile intentionally differs from upstream's cached certifi-backed context in object identity and trust roots.

These changes apply to fresh imports and regenerated wrappers. Automatic refresh of existing installed wrappers remains pending. Original package files and licenses are preserved.

Focused own-code checks passed 61 host tests and 25 TLS/event tests. The **Stage 8 local snapshot, 27 October 2026**, completed 2,490 Python tests OK (two skipped), 243 Node.js runner tests across 48 JavaScript test files, 149 browser tests and configured checks, all with actual exit status zero; the whitespace check also passed. Existing HTTPError/BufferedReader ResourceWarnings and asyncio deprecation warnings remain. Node.js runner, file and supplemental custom-harness counts remain separate. These results establish the bounded adapter contracts, not an original fetch action, an authenticated peer TLS handshake, real service/provider acceptance or device behavior. ## Supported initial contracts

- Native DOM rendering for elements, fragments, function/class components, keyed identity, refs, context, client state/reducer/memo/callback/effect hooks and external-store subscriptions. SVG and native DOM events are included. This is a subset, not a replacement claiming complete React compatibility.
- Framey implementations of selected panel, field, button, dropdown, checkbox, text, slider and loading controls. These use Framey's own surfaces and events. Long third-party panels remain scrollable and report `layout.overflow`; they are not falsely labeled as satisfying Framey's no-scroll main-screen layout.
- Plugin-local custom routes open in a Framey-owned dialog, with route parameters and local navigation history. The main panel keeps its state. This does not supply Steam's global routes, library/store pages or internal component tree.
- `SidebarNavigation` supplies selected plugin-local pages with identifiers, visibility, controlled/uncontrolled selection and keyboard tab navigation. Pages mount on first selection, retain visited content while hidden/inert, and unmount when removed, hidden from the page list or disposed. Routed/link props and unavailable controlled pages fail explicitly; this does not provide Steam navigation or route reporting.
- Selected plugin modals render inside the owned iframe with Framey-authored `showModal`, `ModalRoot`, `ConfirmModal` and dialog containers. Close/cancel handling, focus restoration and retained panel state have local browser evidence. Popout/external window contexts are unsupported. The supported slice has focused regressions and independent review; it does not establish that every original confirmation or modal action works.
- Selected external HTTPS link requests use the enabled plugin's scoped Framey `openURL` API. A successful result confirms request acceptance only; browser display, navigation and page contents need separate verification.
- Selected `Menu`, `MenuItem` and `showContextMenu` shapes use Framey-owned transient menus with local lifecycle cleanup. `CloseSideMenus` closes only these owned menus; it does not close Steam side menus. Unsupported shapes and options fail explicitly.
- Selected original PNGs under `assets/` or `dist/assets/` are embedded from the verified archive. The profile allows at most 64 images, 256 KiB per image, 512 KiB combined, 4,096 pixels per dimension and four million pixels per image. Omitted files and unsupported package-name bindings are recorded in provenance; original files and package identity remain unchanged. CSS, fonts, SVG, scripts, remote images and module chunks are outside this image profile.
- Modern frontend calls use positional arguments and reject failures; legacy calls use keyword arguments and return success/result envelopes. Backend API version and frontend connection version are separate concepts.
- Original Python `Plugin` lifecycle, plugin-local imports, `decky`/`decky_plugin` environment constants, event forwarding, settings directories and the shared `settings.SettingsManager` data contract. Shared settings stay within the plugin's own config/data/log roots. Selected user helpers report the actual normal account and reject root or mismatched effective identity. Original bundled helper modules take precedence. Framey identifies itself truthfully rather than reporting an installed Decky version.
- Per-plugin backend process use through existing Framey workers. Generated backend manifests request keepalive so ordinary idle shutdown does not interrupt timers and event sources; normal worker capacity and resource limits still apply. The adapter is trusted-plugin code, not a security sandbox. Disabling/reloading a plugin releases its host, listeners, effects, pending calls and owned resources.

Native Framey plugins can call `api.steam.read("visibleApps")`, `api.steam.read("app", { appId })` and `api.steam.read("focus")` for fixed cached reads. Success returns the full typed `{ ok: true, available: true, source, data }` envelope. `source` identifies the app-store cache or focus cache; unauthorized, unavailable, stale and malformed reads reject with a fixed code. Plugins cannot supply JavaScript, target identities or transport endpoints. This native API does not supply arbitrary original `SteamClient` or router contracts.

`visibleApps` reports a bounded visible cached list, with at most 4,096 projected records, `visibleCount` and `truncated`; it is not an inventory of all owned or running games. `app` returns a cached app record or explicit `not_found`. The four `steamDeckCategory`, `steamOsCategory`, `steamMachineCategory` and `steamFrameCategory` values are raw Steam cache numbers, with `null` for missing values. They are not ProtonDB ratings, verified Steam Frame support or interpreted compatibility labels. `focus` returns four window/app/overlay scalars and an `empty`/`present` status; those scalars do not establish the running game or current VR scene.

The service checks the enabled caller identity and generation, uses only selected existing Steam contexts, excludes Framey and injection-tainted targets, invalidates stale leases, bounds requests/results and drains owned work at shutdown. These are implemented lifecycle rules with independent review and local test evidence. A controlled Chromium check used the actual root host, target discovery, WebSocket primitive, ownership check and production service/data/transport layers against a synthetic Steam-route page. Its 36 assertions covered navigation invalidating old leases, recovery through fresh reads, revoking one caller while another continued, and drained readers, writers and shutdown work. This verifies the controlled transport path; the separate device check below has its own narrower scope.

A private ARM64 headset run then used a copied production root and fixture plugin identity through token authorization, core dispatch and the actual cached-read service. It returned a valid, untruncated visible-library projection and an empty focus result with four numeric scalars, using four fixed evaluations. The real host, WebSocket, ownership and target/caller guards remained active. Shutdown left no new pending tasks, socket counts and SteamVR process identities were unchanged, and the private bundle was removed. This checked `visibleApps` and `focus` in that private instance; it did not reuse the live core's ownership registry, deploy a plugin UI, test `app` lookup, exercise real focus/navigation transitions or establish native JavaScript frontend delivery.

Existing legacy settings are not silently relocated. Migration helpers validate every supplied source: absent sources return an empty destination mapping without writes, while any existing source causes an explicit unsupported error. Path errors are not treated as absence. The compatibility profile does not grant administrator access or add native-code emulation.

## Evidence and what it does not establish

### Versioned backend result profile

Freshly generated frontend/backend pairs select `framey-rpc-value-v1` result framing. Successful plugin values containing an `error` field remain ordinary plugin data; the host unwraps one strict versioned envelope. Transport and execution failures retain the existing error path. Generated pairs record the selection in `framey_features.rpc_envelope`; existing installed wrappers are not refreshed automatically, and mixed old/new pairs are unsupported.

The framing adds 42 serialized bytes within the existing Worker payload limit, so an opted-in result close to that limit can fail with `too_large`. Owned generated-wrapper, in-process Worker JSON and host checks cover this contract; original frontend workflows, Supervisor resource-limit installation and live headset delivery remain separate acceptance work.
