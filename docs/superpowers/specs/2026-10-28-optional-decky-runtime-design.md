# Optional Decky runtime

## Intent and requirements
Framey must work as a native plugin platform with the Decky compatibility package physically absent. Decky support is an independently versioned, optional user-space download, off by default on new installations and upgrades. Settings explicitly installs/verifies/enables or disables it. A separate remove action preserves imported packages, originals, user settings and individual enable preferences. Store closure does not stop enabled plugins. No React, ReactDOM, Preact or Decky Loader implementation dependency enters core. Original plugin licenses remain intact.

Keep the existing accordion launcher, separate tool windows, pagination and first-party/native workflows. Complete substantial initial implementation before later limited maintenance. Native Framey can evolve independently through a versioned runtime ABI. Hardware/plugin feature compatibility is a separate claim from successful package separation.

## Approach
Retain a small fixed core broker and frontend forwarding facade; move the renderer/helpers, Decky catalog/importer and code service into a dedicated source package and release archive. This reuses the implementation while making installation, activation and shutdown explicit. A file-presence flag alone fails because old wrappers embed their own copies. A separate loader process for all services would be a larger unrelated redesign. Reopening the frozen frontend extension list is unnecessary.

The runtime source directory is `decky_runtime/` (a Python package with relative optional imports and frontend/compat resources). Installed immutable revisions live outside the loader swap tree: `HOME/.local/share/framey/runtimes/decky/versions/<archive_sha256>`. Core state is a dedicated strict bounded `CONF.parent/decky-runtime.json`; this is the single authority rather than duplicating enabled state in ordinary prefs. Missing/corrupt state denies Decky only. Native APIs remain core.

## Contracts
`fy_decky_runtime.py` is the mandatory broker: side-effect-free `status(host)`, `allowed(host, manifest)`, `acquire(host)`/`current(host, handle)`, async `set_enabled(host, enabled)`, `remove(host)`, `shutdown(host)`. Core-only routes: `decky_runtime_status`, `decky_runtime_enable` with exact `{enabled:bool}`, `decky_runtime_remove`. Status separates installed, effective/requested enabled, version, generation, phase and bounded errors. Code issue/touch/revoke and Decky catalog RPCs forward only through an admitted current generation. The runtime entry is a fixed package `runtime.py`, loaded in a fresh private namespace; no arbitrary caller path/module/URL or global sys.path mutation.

The frontend retains a small fixed `api.compat` facade, including existing modules signatures and new `mount(container, descriptor)`. A private verified provider resolves lazily after native plugins have bound; it never downloads implicitly. Provider ABI1 exports `attach(context)` returning modules/mount/dispose. Context contains only plugin-bound API/requests, alive/generation checks, cleanup and owned lost-event delivery; never CORE_TOK. Runtime bundle delivery is caller-bound through the core broker; only first-party verified package bytes may become executable factories. Native Store works without importing a Decky provider. The Decky page is loaded only after explicit enable.

Generated imported wrappers become thin matched frontend/backend stubs using core-owned capabilities. Backend resolution comes from a parent-issued runtime descriptor, not plugin-selected paths, and is gated before original imports. Preserve original vendor paths/data roots and RPC result-envelope version1. Core identifies managed/legacy imports from explicit metadata/managed receipts, never ID prefixes. All legacy embedded copies are inert until a safely matched paired refresh; unknown/custom copies stay explicitly unavailable, with data retained.

## Installation and lifecycle
Use fixed first-party GitHub release metadata, bounded archives, compatible manager/core API/profile/platform and exact archive/file digests. Hash verification is not labeled a publisher signature. Verification policy must be explicit and must not borrow Fan Control root/signature authority. Build a deterministic runtime archive and metadata locally; do not fabricate a published artifact, successful remote download or signed release. No deployment/publication is implied by local tests.

Disable first closes admission and advances a durable generation, then retires Decky callers/tokens, pending imports, frontend handles and module graphs, stops/forgets only Decky workers and drains listeners/handlers. It must reject late activation/commit/reload and preserve native workers. Never use module uninstall/purge to remove the runtime; those can execute vendor hooks or erase preferences. Re-enable creates a fresh service generation. Shutdown drains without clearing durable enable intent. Failed activation/removal is reported honestly; rollback cannot override a newer disable.

Core/app distributions must exclude optional payloads, not merely remove their MANIFEST entries. Source ZIP download size and installed payload size are distinct. Core/app updates and recovery must not restore runtime bytes or activate old ungated wrappers. Versioned runtime installation survives normal loader swaps; core/runtime ABI mismatch disables Decky alone. Full app uninstall retains its existing user-data semantics but also removes its owned runtime location.

## Verification and scope
Prove a physically core-only distribution in a fresh isolated interpreter, without checkout/sys.modules fallbacks: startup, native Store sources/list/install, native worker/SDK calls/reload, settings and core update/recovery. Owned runtime fixtures cover download/verification failure, concurrent enable, disable/remove during imports/mount/RPC/code issuance, stale callbacks, worker/listener drain, data preservation and fresh re-enable. Preserve existing native and compatibility tests, migrating fixture roots to the source package. Run relevant focused tests during implementation, configured checks and complete suites at final integration; use at most four browsers, normally one. Original116-plugin runs and headset actions remain paused. No commits, pushes, releases, root actions or service restarts during this implementation.
